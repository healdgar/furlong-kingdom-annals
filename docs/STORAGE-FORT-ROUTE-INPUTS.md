# Storage routes and fort gate work: operation-local reuse

This is a read-only dependency note for the storage/fort route profile. The optimization ideas are proposals only; no source changes or tests were made.

## Current route and graph call path

`storageRouteBatch` (`index.html:4736`) uses a `WeakMap` entry scoped to one synchronous callback and deletes it in `finally`. The entry reuses a graph reference plus endpoint and path maps. It does not hold fort geometry or gate arrays. `storageRoute` (`:4737`) refreshes its stored street graph from a live signature, clears endpoint/path maps if the graph changes, and then finds nearest reachable nodes using `storageAccess` (`:4728`). Storage quotes can ask for a market route and the minimum route to multiple tilled fields (`storageSiteQuote`, `:4827`); investment surveys try a bounded set of sites (`storageInvestmentSites`, `:4836`); and daily carriage can compare multiple facilities (`storageTick`, `:4820`). Thus a single synchronous route batch can issue many access checks against one unchanged settlement geometry.

`streetGraph` (`:5092`) first builds `fortKey` from `fortCircuits`, wall progress, damage, and each circuit’s `wallR`, then walks street runs through `fortStreetRuns`. Each sampled point in a run may call `fortRoadBlocked` (`:2232`), which enumerates `fortCircuits` again, samples the selected circuit's `wallRadAt`, and calls `fortGateAngles` for each near-wall check. `roadAccessClear` calls this same blocker while graph nodes and edges are joined. `storageAccess` also calls `fortCircuits` to select its sample spacing and invokes `fortRoadBlocked` at each sampled point. A near-wall route can therefore repeat circuit-list construction and ask for gate angles many times in one graph build or route batch.

## Reusable data and its complete live inputs

An operation-local context can hold the current circuit object list and lazily resolve one gate-angle array per circuit. For a given settlement/circuit, `fortGateAngles` (`:2230`) returns one of: worker-provided `renderGates`, a nested circuit's explicit `gates` or fallback `gateA`, or the settlement's cached `_gates` / a fresh `wallGates` result. `wallGates` (`:7779`) derives town gates from current street points/status/traffic, associated building frontage and household counts, and each connected world's current drawn/path geometry. Under native synchronous read-only evaluation, these values do not change between the repeated wall checks in one graph build. `fortCircuits` (`:2229`) enumerates the town curtain, outer wall, current ring, and motte; `fortRoadBlocked` also reads circuit center/radius arrays, wall kind/build/damage/breach state, and current day/progress.

The circuit list and gate arrays must be discarded when that synchronous graph/route operation ends. They must not become a cross-day cache. Relevant writers are distributed: live street stop/open/growth and layout paths (`layoutSettlement`, `:2326`; live operations around `:3265-3267`; growth around `:11650-11659`), road replacement (`stitchRoads`, `:3412`), curtain/castle construction and preparation (`setRectWall`, `:2204`; `fortPrepare`, `:2242`; live wall operations around `:3175-3285`), wall damage/repair (`damageWalls`, `:7413`; castle repair paths; siege/breach writers), razing (`:7256-7258`), and `_gateTrafficVersion` updates (`:15404`). Settlement day and wall-build progress are inputs through `wallProg`/`wallBuilt` (`:7391-7392`). Existing settlement gate cache key (`fortGateAngles`/`settleFortGates`, `:2230-2231`) includes street count, `wallR`, and `_gateTrafficVersion`; it is not a proof that all source arrays are unchanged, so this proposal relies only on synchronous operation-local reuse, not on the persistent gate cache as a validation certificate.

## Safe boundary and callback conditions

The narrowest safe first step is inside one `streetGraph` call: capture `fortCircuits(s)` once and lazily memoize the result of the current `fortGateAngles(s,c)` once per circuit in a local map used by that graph's fort checks. Keep the original radial interpolation, wall progress, kind, build, damage, and breach predicates live and in their current order. Do not write the local arrays back to `s`; do not precompute a town gate list eagerly when no point reaches a wall. This removes duplicate list construction and repeated `wallGates` derivation without changing the exact geometric checks for native pure helpers.

The same local context could be carried by `STORAGE_ROUTE_BATCHES` for repeated `storageAccess` samples, but only for a native, synchronous batch whose route geometry cannot be mutated while the context is in use. The batch wrapper accepts an arbitrary callback, so it cannot assume that every caller is pure. Current native paths include read-only `storageSiteQuote` surveys, `storageInvestment` site comparisons before its final commission, and storage carriage route checks while inventory moves. Their normal stock/project writes do not alter walls or streets, but the native layout/site callback and routing helpers are replaceable. Any implementation should enable the context only when the relevant helper identities and layout callback are the expected native functions, avoid re-entrant use, and fall back to today's calls for patched functions or an operation that can mutate route geometry. Clear the context on every exit, including exceptions. No cached gates should survive a call boundary.

Instrumentation reported `tickStorage` at **217.841 sampled CPU ms/day**, `storageRouteBatch` at **223.9 sampled CPU ms/day**, `streetGraph` at **206.77 sampled CPU ms/day**, `fortRoadBlocked` at **181.27 sampled CPU ms/day**, `wallGates` at **168.2 sampled CPU ms/day**, and `wallRadAt` at **60.063 sampled CPU ms/day** for the AD1350 seed-1001 profile. These are sampled profiler costs, not simulation throughput or elapsed wall-clock time per day. A local gate/circuit context is a targeted candidate for duplicate work; it does not establish that all of the profiled cost is removable or that profile totals are additive.
